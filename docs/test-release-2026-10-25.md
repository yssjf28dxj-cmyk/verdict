## Проверка перед облачными изменениями

Из корня репозитория:

```sh
node scripts/check-test-release.cjs
node --test tests/release/*.test.cjs
```

Проверка не обращается к Firebase, не собирает приложение и не читает ключи.
Она сверяет тестовый Android-проект и bucket, базу `default` без скобок,
правила/индексы, Node 22, изолированный Hosting приглашений, публичный отпечаток
App Links и существование функций из списков развёртывания. Встроена перед
облачными действиями foundation/deadlines-скриптов и добавлена в CI.

Отпечаток закреплён по сертификату APK 4004. Это проверка файла ассоциации,
а не повторная проверка наличия закрытого ключа или сертификата нового APK.
Ключ ранее был найден; в этой подготовке его не открывали и не изменяли.

## Проверка готового APK перед передачей

Когда общая сборка будет отдельно согласована и создана:

```sh
node scripts/verify-test-apk.cjs /path/to/update.apk "$ANDROID_HOME/build-tools/36.0.0"
```

Нужны Java и Android SDK build-tools. Скрипт ничего не собирает, не устанавливает,
не подписывает и не читает хранилище ключей. Он вызывает apksigner verify и aapt
без shell, проверяет пакет, versionCode строго выше 4004, единственный сертификат
с прежним публичным отпечатком, записывает SHA-256 содержимого и размер в JSON
на стандартном выводе. При ошибке инструментов или несовпадении завершает работу
с ненулевым кодом. Изменение файла во время проверки также отклоняется.

Проверено настоящими SDK-инструментами на сохранённом APK 4004: пакет, сертификат,
размер 101007353 байта и SHA-256
`0bced3e5f139547a165362d21f16a988f56fe7182aa9a9beaf8684abba796bb6`
совпали. Как обновление он ожидаемо отклонён из-за versionCode 4004.
Новый APK для этого не создавался. Сценарий успешного допуска нового номера
проверен тестовыми ответами инструментов; реальной новой сборки ещё нет.

Успешная проверка файла не доказывает сохранение UID на устройстве, совместимость
с развёрнутым сервером или работу iOS. Эти пункты остаются в приёмке ниже.

## Совместимость установленного клиента

В исходниках сохранены прежние ветви sendDebateMessage без новых полей запроса,
sendWorldMessage с clientRequestId и без него, а также прежние методы медиа. Новая отправка
текста выбирается по наличию новых полей, а не просто по факту обновления сервера.
Запросы сверены с исходниками da4669c: APK 4004 передаёт debateId/text/senderName
для текста дебатов, debateId для yieldTurn и text/clientRequestId для World Chat.
Медиа используют uploadDebateMedia, затем sendDebateMessage с mediaPath.

Добавлены шесть регрессионных проверок в
`tests/firestore/apk4004-compatibility.test.js`: прежний текст и читаемая схема
сообщения, ограничения роли/срока/завершения, запрет заблокированным и без авторизации,
World Chat с повтором запроса, ещё более старый World Chat без ID и точная серверная
передача хода без expectedTurn. Для последней проверяется настоящая транзакция
контроллера, внешняя очередь и часы подменены; это не вызов Cloud Tasks в облаке.

Целевой прогон с Firestore/Storage: 56 успешных проверок, включая эти шесть и
50 существующих проверок медиа/Storage. Старый двухшаговый путь фото и аудио
проверяет реальные серверные обработчики с эмулятором хранилища. Тестовый проект
эмулятора использует базу (default), не облачную именованную default; её выбор
проверяется отдельно, а реальное развёртывание остаётся этапом приёмки.

Это подтверждение серверных контрактов в эмуляторах, а не запуск бинарного
APK 4004 против развёрнутого сервера. Проверку старого клиента нужно выполнить
до установки нового. Новых гарантий доставки при повторе старого текста дебатов
без ID нет: такой запрос не позволяет серверу отличить повтор от нового сообщения.

## Последовательность приёмки

Foundation-скрипт теперь заканчивает облачные команды проверкой всех 37 ожидаемых
функций из обоих списков развёртывания. `verify-test-backend.cjs` запрашивает
`gcloud functions list --v2 --project=verdict-test-1471f --format=json` и требует
ACTIVE, GEN_2 и nodejs22 именно в us-central1 тестового проекта. Отсутствующие,
ещё развёртываемые или ошибочные функции дают ненулевой код; итоговое сообщение
об успешном прохождении скрипта не выводится. Проверку можно запускать отдельно:

```sh
node scripts/verify-test-backend.cjs
```

Это чтение состояния, не проверка фактического коммита кода, IAM, доставки задач,
правил, индексов или FCM. Здесь нет gcloud и доступа к облаку: реальная проверка
ещё не выполнена. Шесть тестов используют искусственные ответы API и проверяют
отказы при неполном/неверном ответе. Локально подтверждён также отказ при отсутствии
gcloud. Владелец выполняет развёртывание в своём авторизованном Cloud Shell с Node 22.

1. Зафиксировать точный коммит общего пакета и пройти локальную проверку выше.
2. В VERDICT Test проверить реальные ресурсы, права служб и провайдеры входа.
   Только затем выполнить тестовое серверное развёртывание. Автоматическая
   миграция старых данных не является частью разрешения обновить сервер.
3. На установленном APK 4004 проверить вход, текст, голос, передачу хода и завершение.
   При отказе исправить совместимость до передачи нового клиента.
4. Проверить тестовый Hosting приглашений и настроить провайдеры, которые действительно
   включаем. Google остаётся выключенным до настройки OAuth. Ссылки включаются
   только после публикации и проверки соответствующего сайта.
5. После отдельного указания собрать одну общую тестовую APK. Подтвердить пакет
   com.example.verdict.test, versionCode выше 4004 и совпадение сертификата.
   Сохранить коммит, SHA-256 файла, отпечаток сертификата и предыдущий APK.
   При несовпадении подписи остановить выпуск; не создавать новый ключ взамен старого.
6. Установить поверх без удаления приложения и очистки данных. Проверить возврат
   к прежнему UID и ролям, затем два независимых аккаунта и зрителя.
7. Пройти создание/отмену/принятие, текст/медиа с потерей сети, банк времени,
   закрытые клиенты, голоса, результат, реванш, историю, избранное и реакции.
8. Отдельно проверить FCM: отказ/выдача разрешения, фон/запуск из уведомления,
   смена профиля, два устройства и повтор события. Эмулятор отправитель подменяет.
9. Записать измерения задержек и ошибки устройства; повторять нужные проверки
   после исправлений. Готовность iOS подтверждается отдельной Apple-сборкой
   и настоящими iPhone/iPad, а не Android-тестами.

Main, production Firebase и магазины не входят в эту последовательность.
