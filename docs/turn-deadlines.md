# Своевременное переключение хода — тестовый проект

## Проблема и границы изменения

Тест 22 октября выявил заметную паузу после нуля. В прежнем коде клиент
и сервер ожидали 7 секунд для загрузки медиа, а резервная серверная проверка
выполнялась раз в минуту. Если бойцы закрыли приложение, быстрый клиентский
вызов отсутствовал. Это источники задержки в коде, а не измерение конкретного
запуска пользователя. Загрузка медиа остаётся отдельной нерешённой задачей.

Новая схема активна только в verdict-test-1471f (Firestore `default`).
Проект verdict-final и ветка main не публикуются и не меняются.

## Поведение

- Firestore-триггер scheduleDebateTurnDeadline ставит Cloud Task на roundEndsAt.
  Наличие открытого приложения не требуется.
- advanceDebateTurnTask — закрытая серверная функция. Клиентам и зрителям
  права её вызова не выдаются.
- Задача содержит раунд, спикера и deadline. В Firestore-транзакции проверяется
  соответствие текущему ходу. Дубли не переключают очередь дважды; устаревшая
  задача после изменения срока или завершения дебата ничего не меняет.
- Следующее время окончания вычисляется от предыдущего deadline, не от
  момента получения задачи. Если приложения были закрыты долго, просроченные
  ходы пропускаются по серверному расписанию вплоть до завершения боя.
- Досрочное завершение хода не отнимает у следующего бойца старые 7 секунд.
- На тестовом сервере нет обязательной 7-секундной паузы. Сообщение после
  окончания хода отклоняется, даже если событие переключения ещё доставляется.
  Поздние медиа не принимаются; будущий механизм резервирования загрузки сюда
  не входит. Старый APK остаётся совместим, но его клиентский запасной вызов
  всё ещё ждёт 7 секунд; основное переключение теперь серверное.
- Сбой enqueue после записи перехода можно повторить без повторного перехода.
  Firestore-триггер повторяется при ошибках, Cloud Tasks повторяет доставку,
  минутная проверка остаётся страховкой.
- Метаданные просмотра не порождают новые задачи. Детерминированный task ID
  исключает дубли одной задачи. События Firestore могут приходить не по порядку;
  перед enqueue всегда читается актуальный документ.

Cloud Tasks не является таймером жёсткого реального времени. Холодный старт,
задержка события или сеть могут превысить 1 секунду. minInstances остаётся 0:
постоянно тёплые экземпляры и дополнительные постоянные расходы не включены.
Лог `debate.deadline.processed` содержит scheduledAtMs, latenessMs, changed,
чтобы измерить реальные задержки после тестовой установки.

## Что будет делать установка (ещё не запускалась)

Скрипт включает Cloud Tasks API в тестовом проекте. Затем выдаёт существующему
runtime service account роль cloudtasks.enqueuer в тестовом проекте и
iam.serviceAccountUser только на самого себя (для OIDC-подписи задач).
Сначала публикует закрытый обработчик задач, затем разрешает этому же аккаунту
run.invoker только на его Cloud Run сервис. После этого публикует триггер и
обновляет четыре существующих функции. Пользовательские роли доступа к данным,
Storage, Hosting и Firestore rules не меняет. Не применяет миграций и не удаляет
данные. Cloud Tasks и дополнительные вызовы Functions оплачиваются по Blaze
после бесплатных квот; ограничение числа экземпляров не ограничивает счёт.

Проверки до публикации: серверная сборка; 39 серверных тестов; 12 сценариев
в эмуляторе Firestore; 24 прежних проверки медиа. Скрипт проверен bash -n.
Публикация, настройка IAM и реальная доставка Cloud Tasks ещё не проверены.

## Приёмка после установки

1. Создать НОВЫЙ текстовый дебат: два реальных аккаунта, 1 раунд по 30 секунд.
2. Проверить переход от первого ко второму и завершение, записать задержку.
3. Повторить, закрыв приложения обоих бойцов. Вернуться после окончания боя:
   должен быть завершён, без нового полного таймера с момента открытия.
4. Проверить, что прежний боец не может отправить сообщение после срока,
   второй не может писать раньше своей очереди, зритель писать не может.
5. Проверить досрочную передачу хода, повторное открытие комнаты и голосование.
6. Сопоставить фактическую задержку и логи задачи. Не считать ACTIVE доказательством
   успешного исполнения очереди или достижения задержки менее секунды.


## Исправление установки очереди

Firebase CLI 14.27.0 cloudtasks.setEnqueuer вызывает existing.bindings.filter
без проверки отсутствующего bindings. При явном invoker: private для пустой
политики очереди это приводит к TypeError после создания функции. Явный
invoker убран: onTaskDispatched по умолчанию закрыт, а существующий скрипт
назначает run.invoker только серверным service accounts. Публичный доступ
не включается; права администратора пользователю из-за TypeError не добавляем.
Перед повторной установкой скрипт задаёт 7-дневную очистку кэша образов сборок
в тестовом Artifact Registry. Она не удаляет Firestore/Storage данные или
работающие функции. Реальную IAM-политику после установки нужно проверить.
