# Доступ к медиа

## Обновление 23 октября 2026

Новый клиент загружает до 6 МиБ через `uploadDebateMedia`: сервер проверяет
доступ по выбранной базе, пишет в закрытый `debates/{id}/uploads/` и возвращает
путь. SDK не может читать этот файл или получать download URL. Затем
`sendDebateMessage` заново проверяет ход, публикует защищённую копию и удаляет
новую временную загрузку. Это устраняет зависимость staging-загрузки от
Storage Rules, которые обращались к другой базе `(default)`.

Нужны новый APK, Functions и правила. В реальном Firebase и на микрофоне
планшета этот пакет ещё не проверен. Эмулятор проверяет доступ и передачу
байтов, а не аудиокодек. Старые token URL не мигрированы; возможные аварийные
временные объекты требуют отдельной политики хранения.

Полный статус: [проверка фундамента](foundation-audit-2026-10-23.md).

## Новые сообщения

1. Flutter загружает файл в `debates/{id}/media/{timestamp}_{uid}.{ext}`.
   Загрузчик возвращает путь, не запрашивая `getDownloadURL()`.
2. `sendDebateMessage` проверяет авторизацию, право говорить, путь, владельца
   по имени загрузки, наличие файла, тип и размер менее 10 МиБ.
3. Для нового поля `mediaPath` сервер читает загрузку и записывает отдельную
   копию в `debates/{id}/secured/{messageId}.{ext}` через Admin SDK. Метаданные
   временного файла и его токен не копируются.
4. Сервер удаляет только эту новую временную загрузку до публикации сообщения.
   Если удаление не удалось, сообщение не публикуется. Если транзакционная
   повторная проверка хода не прошла, защищённая копия удаляется best effort.
5. Сообщение хранит `mediaPath`, не постоянную ссылку. Правила запрещают прямое
   чтение и запись `secured` со стороны клиента, включая получение метаданных.
6. `getDebateMedia` проверяет авторизацию и актуальный доступ к дебату,
   ограничивает размер и возвращает байты в base64. Ссылки он не выдаёт.

Для ограниченного MVP используется callable-прокси: это проще проверить,
чем отдельный потоковый сервер. Base64 добавляет примерно треть объёма,
а сервер участвует в каждом скачивании. Память обеих медиа-функций задана
512 МиБ, параллелизм — 4 запроса на экземпляр. Это ещё не решение для
массового Live Audio/Video. Байты ограничены 10 МиБ; проверка на устройстве
должна охватить крупные изображения, длинные записи и медленную сеть.

## Совместимость и границы

- Новый клиент извлекает путь из старого `mediaUrl` и скачивает его через
  callable; URL с токеном напрямую не открывается. Принимаются только
  Firebase-ссылки собственного bucket и пути текущего дебата.
- Сервер принимает старые URL-запросы отправки и сохраняет для них совместимое
  поле. **Это старый режим: его токены не отзываются и его файлы не мигрируют.**
- Новые изображения загружаются в память. Для аудио создаётся отдельный
  временный файл; при закрытии проигрывателя выполняется best effort удаление.
  Прежний кэш, оставшийся от старых версий, автоматически не очищается.
- Отзыв одобрения запрещает следующий запрос. Уже скачанные байты, скриншоты,
  записи и память открытого виджета нельзя отозвать дистанционно.
- Запрещены перезапись объекта и изменение метаданных клиентом: иначе можно
  было бы заменить доказательство или вернуть токен. Для create дополнительно
  проверяется `resource == null` (в том числе для поведения эмулятора).
- Удаление собственного сообщения поддерживает пути `media` и `secured`.
- Повтор отправки после потери ответа пока не имеет отдельного ключа
  идемпотентности. После успешной отправки временный файл уже удалён;
  отладку повторной отправки нужно включить в проверку реального клиента.
- Аварийное завершение функции между операциями с Storage и Firestore может
  оставить неиспользуемые объекты. План очистки таких объектов — отдельная задача.

## Проверки

Из корня проекта, с Node.js 20 и активированными локальными инструментами:

```sh
cd functions
npm ci
npm run build
node --test test/*.test.js
cd ../tests/firestore
npm ci
npm run test:storage
```

Последняя команда запускает Firestore и Storage для `demo-verdict-rules`.
Перед тестами собирается настоящий TypeScript-код Functions. Тесты вызывают
его обработчики `.run()` с эмуляторами, включая реальную запись защищённой
копии, удаление временной загрузки и отказ доступа посторонним. Это не проверка
сетевого транспорта Cloud Functions и не запуск мобильного интерфейса.

Flutter:

```sh
flutter analyze --no-pub lib/services/media_upload_service.dart lib/services/media_download_service.dart lib/utils/debate_media_path.dart lib/widgets/debate_messages_list.dart lib/screens/debate_room_screen.dart test/debate_media_path_test.dart
flutter test --no-pub test/debate_media_path_test.dart
```

Использован Flutter 3.41.4, `pubspec.lock` не изменялся.

## Перед выпуском

Ничего из этого этапа не опубликовано в действующий Firebase.
Нужен согласованный выпуск Functions, правил Storage и совместимого клиента
с проверкой на устройстве: старый APK не отображает новое поле `mediaPath`.
Для защищённых объектов нельзя сначала включать новый клиент без нового
серверного обработчика и правил.

Старые токены и уже существующие медиа действующего проекта здесь не менялись.
Отзыв старых ссылок требует отдельного плана с проверкой совместимости,
перечнем затрагиваемых объектов и согласованием владельца проекта.
