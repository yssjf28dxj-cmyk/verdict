# Локальные проверки доступа Firestore

Этот набор проверяет желаемые границы приватности на настоящем эмуляторе
Firestore, используя текущий `../../firestore.rules`. Правила не исправляются
и не подменяются. Набор может завершаться с ошибками, пока уязвимости не устранены.

## Запуск

Нужны Node.js 20, npm и Java 21. Из корня репозитория:

```sh
cd tests/firestore
npm ci
npm test
```

В подготовленной облачной среде сначала активируйте установленный Node.js:

```sh
export PATH="/workspace/.onboarding/tools/node_modules/.bin:$PATH"
export npm_config_cache=/workspace/.onboarding/npm-cache
export XDG_CACHE_HOME=/workspace/.onboarding/cache
export XDG_CONFIG_HOME=/workspace/.onboarding/config
export FIREBASE_EMULATORS_PATH=/workspace/.onboarding/cache/firebase/emulators
```

Firebase CLI при первом запуске скачивает эмулятор с `storage.googleapis.com`.
Этот домен должен быть разрешён в сетевых настройках среды. Порт 8085 должен
быть свободен. Интерфейс эмулятора отключён.

Команда запускает только Firestore с фиктивным проектом `demo-verdict-rules`,
выполняет тесты и останавливает эмулятор. Ключи Firebase и вход в аккаунт
не требуются. Перед запуском создаётся игнорируемая точная копия правил
`firestore.generated.rules`: Firebase CLI не допускает путь за пределами
своего каталога проекта. Исходный файл правил остаётся неизменным.
Тесты отказываются запускаться без локального адреса эмулятора.
Не используйте эту команду против общего эмулятора с нужными данными:
перед каждым тестом очищаются данные фиктивного проекта.

## Что проверяется

- Участники читают приватный дебат и сообщения, посторонние — нет.
- Запрос списка не обходит приватность.
- Одобренный зритель читает сообщения дебата «по заявке».
- Без одобрения сообщения недоступны, в том числе после подачи заявки.
- Создатель может одобрить заявку.
- Отзыв одобрения закрывает доступ; отсутствие списка одобренных не открывает
  сообщения посторонним. Запрет действует и для чтения списка сообщений.
- Обычные зрители по-прежнему могут читать публичные сообщения.
- Заявка не позволяет добавить ИИ-результат, удалить или изменить тему,
  либо одобрить самого себя.

По статическому анализу исходных правил ожидались нарушения в пяти сценариях:
чтение приватных документов через список, чтение сообщений без одобрения,
чтение после подачи заявки, добавление поля и удаление поля через заявку.
Результаты запусков приведены ниже. Проверки Cloud Functions, интерфейса
и опубликованной базы в этот набор не входят. Storage проверяется отдельной
командой, описанной ниже.

### Обязательная совместимость клиента перед публикацией

Правила Firebase не фильтруют результаты: запрос, потенциально возвращающий
закрытый документ, отклоняется целиком. Flutter-запросы теперь адаптированы:

- `lib/utils/debate_query_access.dart`: общий OR-фильтр — карточки `public` и
  `request_only`, либо совпадение текущего UID с `fighter1`, `fighter2`,
  `creatorId`, `invitedUserId` или элементом `invitedUserIds`.
- `lib/widgets/home_debate_list.dart`: фильтр применяется до сортировки по
  `createdAt` и ограничения 50. Поиск, региональные фильтры и визуальная
  фильтрация остаются дополнительными условиями отображения.
- `lib/screens/public_profile_screen.dart`: тот же фильтр добавлен к обоим
  запросам истории по `fighter1`/`fighter2`, ограничение 20 сохранено.
  Приватный общий дебат доступен участнику и на странице соперника.
- `lib/screens/profile_screen.dart`: собственные запросы не изменены.

Правила участника используют безопасные значения для отсутствующих полей.
Проверка массива приглашений использует `hasAny` без отдельного `is list`,
который мешал эмулятору разрешать `array-contains` в объединённом запросе.
Неверные типы приглашений не дают постороннему доступа — это проверено.
Для списков без явной видимости разрешена только ветка участия: старые
документы без `visibilityMode` не включаются в общедоступную ленту автоматически.

Итог: 45 из 45 тестов прошли, ошибок и пропусков нет. Новые тесты повторяют
структуру клиентских запросов в JS SDK и проверяют содержимое результатов:
все пять ролей участия, приглашения, общую приватную историю и сортировку.
Это не запуск Flutter-интерфейса на устройстве.

Flutter 3.41.4 соответствует ревизии `.metadata`. Команды выполнены из корня:

```sh
export PUB_CACHE=/workspace/.onboarding/pub-cache
export XDG_CONFIG_HOME=/workspace/.onboarding/config
export XDG_CACHE_HOME=/workspace/.onboarding/cache
export ANALYZER_STATE_LOCATION_OVERRIDE=/workspace/.onboarding/analyzer-state
export CI=true
/workspace/.onboarding/flutter/bin/flutter pub get --enforce-lockfile
/workspace/.onboarding/flutter/bin/flutter analyze --no-pub lib/utils/debate_query_access.dart lib/widgets/home_debate_list.dart lib/screens/public_profile_screen.dart
```

Зависимости разрешены без изменения `pubspec.lock`, анализатор сообщил
`No issues found`. Файл `firestore.indexes.json` дополнен индексами для
ветвей OR-запросов ленты и истории. Эмулятор не доказывает наличие и готовность
составных индексов в настоящем Firebase.

Перед публикацией необходимо подготовить индексы в выбранной тестовой среде,
проверить реальные клиентские запросы и согласовать выпуск совместимого APK.
Старые APK с общим запросом ленты будут получать `permission-denied` после
включения новых правил. Правила, индексы и приложение здесь не публиковались.

## Проверки Storage: доступ SDK и ограничение ссылок с токеном

Из этого же каталога с теми же переменными среды:

```sh
npm run test:storage
```

Команда запускает только локальные Firestore и Storage для фиктивного проекта
`demo-verdict-rules`. Требуются свободные порты 8085 и 9199. Перед каждым
сценарием очищаются только данные этого проекта в эмуляторах. Источником
правил служат текущие `firestore.rules` и `storage.rules` из корня репозитория;
для CLI создаются игнорируемые копии без изменения содержимого.

Результат 19 октября 2026: 20 сценариев выполнено, все прошли, пропусков нет.
Из них 19 проверяют разрешения и сохранение загрузки изображений/аудио,
а один — диагностический тест **оставшейся уязвимости** ссылок с токеном.
Зелёный результат этого диагностического теста означает, что обход воспроизведён,
а не что он устранён.

Теперь SDK допускает чтение только вошедшим пользователям: публичных файлов,
файлов своего дебата либо файлов `request_only` после одобрения. Отзыв
одобрения закрывает доступ SDK. Приватный файл не становится доступен зрителю
из-за одного лишь присутствия в списке одобренных. Отсутствующий документ
дебата не открывает доступ. Существующие ограничения загрузки не менялись.

### Текущая схема новых медиа

Затем добавлен защищённый путь `secured` и callable `getDebateMedia`.
Новые сообщения хранят путь файла; сервер создаёт отдельную Admin-only копию
без токена временной загрузки и удаляет эту загрузку до публикации.
Прямой клиентский доступ к защищённым объектам и перезапись файлов запрещены.
Старые ссылки и реальные файлы не мигрировались.

`npm run test:storage` теперь требует установленных зависимостей `functions`:
pretest собирает TypeScript перед вызовом настоящих обработчиков `.run()`.
Последняя серия включает 24 сценария, из которых один специально подтверждает
**незакрытый доступ по старой ссылке**; это диагностический результат, а не
гарантия защиты старых файлов. Отдельно проверены отправка в защищённое
хранилище, отказ прямого SDK-доступа, удаление временной ссылки, выдача байтов
участнику, отказ постороннему и отзы́в допуска перед следующим скачиванием.

Архитектура, команды проверки и ограничения выпуска описаны в
[`docs/media-access.md`](../../docs/media-access.md). Мобильное воспроизведение
и HTTP-транспорт опубликованных Functions ещё не проверены.
